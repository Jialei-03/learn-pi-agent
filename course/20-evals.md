## 测试与评测

第 19 章用脚本模型测试了 mox 的集成：协议、事件顺序、取消。这些是**测试**——被测的是确定的代码，同样的输入总是同样的输出，通过就是通过。

可是你改了一句系统提示，换了一个工具的描述，升级了模型，Agent 是变好了还是变差了？这不是测试能回答的。被测的是模型的行为，同一个任务跑十次，可能成功七次。这需要**评测**（evals）：用一组任务反复运行真实的 Agent，统计结果。

| | 测试 | 评测 |
| --- | --- | --- |
| 被测对象 | 代码 | 模型 + 代码作为一个整体的行为 |
| 模型 | 脚本模型 | 真实模型 |
| 结果 | 通过 / 失败 | 通过率、成本、耗时……的分布 |
| 运行次数 | 一次 | 很多次 |
| 失败意味着 | 有 bug | 一个数据点 |

Pi 的评测说明里有一句话很准确：

@pi packages/evals/README.md#L127-L129

低分是数据，不是基础设施的故障。

几个要点：

- **每次运行一个全新的目录。** 任务之间、变体之间、重复之间互不影响。Pi 走得更远，每次运行一个全新的容器，连家目录、配置目录、会话目录都是新的：

@pi packages/evals/README.md#L88-L88

- **现场是一个 git 仓库**，布置完提交一次，评分时就能精确地知道 Agent 改了哪些文件。
- **运行出错不等于任务失败。** 网络中断、超时是这次观测无效，要单独统计，不能混进通过率。Pi 的报告里，任何一对结果不完整，就不给出总的结论：

## 评分：看结果，不看说法

第 18 章说过，模型说“完成了”不算数。评分也一样：**看最终状态，不看模型怎么说**。四个任务的评分方式：

@code evals/cases.ts#CASES collapse=true

- **隐藏测试**：`fix-bug` 的项目里有一个 `test.js`，但评分用的是另一组更严格的测试，Agent 看不到。只要它能看到评分用的测试，就可能去“迎合测试”（甚至直接改测试），而不是真正把事做对。
- **范围检查**：`stay-in-scope` 用 `git status` 检查改了哪些文件。“顺手”改了别的文件，即使改得没错，也是失败——在真实的项目里，没被要求的改动会给审查的人添麻烦。
- **问答题**也尽量机械地评分：检查关键的命令有没有出现在回答里。

Pi 的做法相同：评测代码在 Agent 运行结束后收集一份结构化的最终状态（文件在不在、配置对不对、命令展开成了什么），再和期望值严格比较：

@pi packages/evals/evals/prompt-templates.docs.eval.ts#L25-L76

对于没法机械评分的任务（“这段解释写得好不好”），可以让另一个模型来评分（LLM-as-judge）。它的问题是评分本身也有随机性和偏好（比如偏爱更长的回答），所以要给出明确的评分标准，并且用一批人工标注过的样本校准它。能用确定性评分的地方，就不要用模型评分。

### 先测评测本身

评分器写错了，评测的数字就毫无意义——而且你不会知道它错了。所以在用真实模型之前，先用几个**已知答案**的脚本 Agent 检查评分器：正确的解必须通过，只说不做必须失败，投机取巧（只满足表面要求）也必须失败：

## 跑几遍才够

@figure assets/course/ch20-evals.png 评测：同样的任务跑很多遍，两个版本成对比较，用区间而不是一个数说话

假设 B 版本真的比 A 好 10 个百分点。每个任务跑 3 遍，能看出来吗？用模拟代替真实模型，可以把这个问题看得很清楚：

@lab node labs/ch20/stats.ts

每个任务只跑 3 遍时，将近五分之一的实验会得出**相反的结论**——你会以为 B 更差，然后把一个好的改动撤回去。要可靠地看出 10 个百分点的差别，需要上百个样本。

几个让结论更可靠的做法：

- **报告区间，而不是一个数。** 12 次里通过 9 次，真实的通过率可能在 47% 到 91% 之间。框架用 Wilson 区间（小样本时比常见的正态近似可靠）：

@code evals/harness.ts#wilson

- **成对比较。** 同一个任务、同一轮，两个变体各跑一次，只看结果不同的那些对。任务之间的难度差异被抵消了，比直接比较两个通过率更敏感。
- **交替顺序。** 奇数轮先跑 A，偶数轮先跑 B，避免“总是先跑的那个”占便宜（比如服务商的缓存、限流）。Pi 的评测计划就是这样排的：

- **标出不稳定的任务。** 同一个变体时而通过时而失败的任务，最需要关注，也最容易误导结论。
- **不要只看通过率。** 成本（token）、耗时、轮数同样是指标：一个通过率高 2 个百分点、成本翻倍的改动，未必值得。

## 一次真实的 A/B 评测

用真实模型（MiniMax-M3.1-Flash）跑四个任务，比较两个变体：A 是 mox 默认的系统提示；B 多一句“改完代码必须实际验证”。每个任务每个变体跑 3 轮：

@include labs/ch20/recorded/live-eval.txt

这次评测的结果本身就是一课：

- **两个变体都是 12/12。** 任务太简单了，模型每次都能做对，评测**看不出任何差别**——Pi 的评测报告专门会标出这种“饱和”的情况。即使是 12/12，95% 区间的下限也只有 76%：12 个样本证明不了“总是对的”。
- **通过率一样，成本却不一样。** 变体 B 的平均输入 token 是 A 的两倍，平均耗时是 2.5 倍；它的一次运行用了 20 轮、150 秒（多出来的验证步骤并不总是那么顺利）。在这组任务上，B 是一个只增加成本的改动。
- **轨迹指标说明了原因。** 在改动了文件的运行里，A 在最后一次修改之后运行命令验证的比例已经是 8/9——这个模型本来就会验证，那句额外的要求针对的是一个已经存在的行为。

所以这次评测的结论不是“B 没用”，而是“这组任务回答不了这个问题”。下一步应该加入更难的任务（多个文件、隐藏的边界情况、需要先读懂代码才能修的 bug），让基线不再是 100%，再比较两个变体。设计评测任务时，先确认基线的通过率落在中间区域，评测才有区分能力。

## 轨迹：怎么失败的

通过率告诉你**有多少**失败，轨迹告诉你**怎么**失败。一次运行的轨迹就是它的全部消息（第 7 章的会话记录），从中可以提取出很多有用的信号：

@code evals/trajectory.ts#summarize

- **重复的调用**：一模一样的工具调用出现了好几次，常常意味着在原地打转。
- **工具出错的次数**：模型是不是在和工具的参数格式较劲（第 4 章）。
- **最后一次修改之后有没有验证**：上面的评测正是用它来检查变体 B 的那句话有没有起作用。
- **token 和缓存命中**：成本异常时先看这里（第 6 章）。

在线上运行的 Agent 里，同样的信息以遥测（telemetry）的形式收集：每次模型请求、每次工具调用都是一个带时间和属性的“跨度”（span）。Pi 的 `telemetry` 包定义了一套不绑定具体后端的接口，可以接到 OpenTelemetry 之类的系统上。评测和遥测是一体两面：评测在上线前回答“变好了吗”，遥测在上线后回答“现在怎么样”，而线上发现的失败，又应该变成新的评测任务。

::: note 公开的基准测试
SWE-bench（修复真实开源项目的 issue）、Terminal-Bench（在终端里完成任务）这类公开基准，衡量的是“模型 + Agent 框架”这个整体。它们适合横向比较，但离你自己的使用场景往往很远，还可能有训练数据污染的问题。真正指导你改进的，是一套贴近自己工作的小评测。
:::

## 面试题

先自己回答，再展开对照要点。

::: interview 你怎么知道对 Agent 的一个改动（提示词、工具、模型）是变好了还是变坏了？
用评测：一组贴近真实使用的任务，每个任务在隔离的环境里运行，用确定性的方式评分（看最终状态，用隐藏测试），两个版本成对地、交替顺序地多次运行。报告通过率及其置信区间、成对比较中结果不同的对数、不稳定的任务，同时看成本、耗时和轮数。样本太少时不下结论。改动上线后，用遥测和线上的失败案例继续补充评测集。
:::

::: interview 怎样为 coding agent 设计评分器？
- 看最终状态而不是模型的说法：运行测试、检查文件、检查 git 改动范围。
- 用隐藏测试，防止 Agent 迎合可见的测试或修改测试。
- 检查“不该发生的事”：改动了无关文件、删除了测试、引入了新的依赖。
- 先用已知答案的样本验证评分器：正确的必须通过，敷衍的、投机的必须失败。
- 区分“运行出错”和“任务失败”。
- 开放式任务才用模型评分，并给出评分标准、用人工标注校准。
:::

::: interview LLM-as-judge 有什么问题？怎么用好它？
问题：评分本身有随机性；有系统性的偏好（偏爱更长、更自信、和自己风格相近的回答，受位置影响）；可能被被评的内容影响（注入）。用法：给出明确、可操作的评分标准和示例；比较式（A 和 B 哪个好）通常比打绝对分数稳定，并交换顺序各评一次；用一批人工标注的样本测它和人的一致程度；能用确定性评分的部分就不交给模型。
:::

::: interview 评测需要跑多少次？两个版本的结果怎么比较？
取决于你想看出多大的差别：要可靠地分辨 10 个百分点的差距，每个变体需要上百个样本；只跑几次时，经常会得出相反的结论。比较时用成对的设计（同一任务同一轮各跑一次，只看结果不同的对），交替运行顺序，报告置信区间而不是单个百分比，并标出不稳定的任务。还要同时比较成本和耗时。
:::

::: interview 评测集会“过拟合”吗？
会。反复针对同一组任务调整提示词，最后得到的是“在这几个任务上表现好”的提示词。缓解办法：留一部分任务只用来做最终确认，不参与调整；持续从真实使用中加入新任务（尤其是线上失败的案例）；关注改动的原因是否通用，而不只是分数是否上升。
:::
