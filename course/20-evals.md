## 测试与评测

第 19 章用脚本模型测试了集成：协议、事件顺序、取消。这些是**测试**——被测的是确定的代码，同样的输入总是同样的输出，通过就是通过。

可是你改了一句系统提示，换了一个工具的描述，升级了模型，Agent 是变好了还是变差了？这不是测试能回答的。被测的是模型的行为，同一个任务跑十次，可能成功七次。这需要**评测**（evals）：用一组任务反复运行真实的 Agent，统计结果。

| | 测试 | 评测 |
| --- | --- | --- |
| 被测对象 | 代码 | 模型 + 代码作为一个整体的行为 |
| 模型 | 脚本模型 | 真实模型 |
| 结果 | 通过 / 失败 | 通过率、成本、耗时……的分布 |
| 运行次数 | 一次 | 很多次 |
| 失败意味着 | 有 bug | 一个数据点 |

Pi 的评测说明里有一句话很准确：

@pi packages/evals/README.md#L127-L129

低分是数据，不是基础设施的故障。

## Pi 怎么评测：文档带来多大提升

Pi 仓库里有一个 `packages/evals` 包，它回答的是一个很具体的问题：**Pi 自带的文档（README、`docs/`、`examples/`）到底有没有让 Agent 做得更好？** 做法是对每个用例跑两个变体：`without_docs` 把这些文档从安装包里删掉，并去掉系统提示里的“文档路由”一节；`with_docs` 是原样的 Pi。同一个模型、同一批任务，比较两边的通过率，差值叫 **lift**（提升）。

几个设计，每一个都是对一种“评测会骗你”的方式的防御：

- **每个运行一个全新的容器。** 新的家目录、配置目录、工作区、会话目录，连容器文件系统都是新的。评测定义、评分器、fixtures 在 Agent 运行时由 root 持有、对 Agent 不可读（harness 权限降级之后）。Agent 看不到评分用的东西，也带不走上一次运行留下的东西：

@pi packages/evals/README.md#L88-L88

- **先排好计划，再执行。** 每个（用例，变体，模型，第几次）先展开成一份完整的计划，执行时哪个运行失败或缺失，只是记一笔，计划里的其他运行继续。下面这个函数就是排计划的，注意奇数次先跑 `without_docs`、偶数次先跑 `with_docs`：

@pi packages/evals/src/plan.ts#createTaskPlan

@lab node labs/ch20/pi-plan.ts

  交替先手，是为了让“总是先跑的那个”占不到便宜（服务商的缓存、限流）。函数开头还有一串校验：用例名必须是 `<eval set> > <case>`，不能重名，模型必须带服务商。评测的数据质量，很大一部分靠这种“拒绝含糊”。
- **成对比较，缺一不可。** 只有 `without_docs` 和 `with_docs` 在同一个（用例，第几次）上**都**恰好产生一个分数，这一对才算数。缺的、重复的、被跳过的、出错的，都会挡住这一对；只要有一对被挡住，整个评测的总通过率就**不发布**：

@pi packages/evals/README.md#L103-L105

- **报告会替你起疑。** 报告里有五种旗：

@pi packages/evals/src/report.ts#comparisonFlags

  `no-lift`：两边通过率一样；`negative-delta`：加了文档反而更差；`control-saturated` / `treatment-saturated`：某一边是 100%，任务太简单，区分不出差别；`flaky`：同一个变体在同一个用例上有时通过有时失败。这些旗是评测的“常识”：**没有差别、太简单、不稳定**，比“有差别”更常见，而且更容易被当成好消息。
- **每次运行留下证据。** `.eval/<时间>/` 目录里有完整的计划（`expected-runs.json`）、每个运行的规范化结果（`observations.jsonl`）、Vitest 的原始 JSON，以及 Pi 自己的会话文件（`session.jsonl`）：出了问题可以回头看每一个运行的完整轨迹。

## 评分：看结果，不看说法

第 18 章说过，模型说“完成了”不算数。评分也一样：**看最终状态，不看模型怎么说**。Pi 的评测代码在 Agent 运行结束后收集一份结构化的最终状态（文件在不在、配置对不对、命令展开成了什么），再和期望值严格比较：

@pi packages/evals/evals/prompt-templates.docs.eval.ts#L25-L76

几条通用的原则：

- **隐藏测试。** 项目里可以有一个让 Agent 看得见的 `test.js`，但评分用的是另一组更严格的测试，Agent 看不到。只要它能看到评分用的测试，就可能去“迎合测试”（甚至直接改测试），而不是真正把事做对。Pi 的做法更彻底：评分器所在的文件，运行时对 Agent 不可读。
- **检查不该发生的事。** 改动了无关文件、删除了测试、新建了多余的文件：用 `git status` 比对基线。在真实的项目里，没被要求的改动会给审查的人添麻烦。
- **问答题也尽量机械地评分**：检查关键的命令有没有出现在回答里。
- **先测评测本身。** 评分器写错了，评测的数字就毫无意义——而且你不会知道它错了。所以在用真实模型之前，先用几个**已知答案**的脚本 Agent 检查评分器：正确的解必须通过，只说不做必须失败，投机取巧（只满足表面要求）也必须失败。实战里会做这一步。

对于没法机械评分的任务（“这段解释写得好不好”），可以让另一个模型来评分（LLM-as-judge）。它的问题是评分本身也有随机性和偏好（比如偏爱更长的回答），所以要给出明确的评分标准，并且用一批人工标注过的样本校准它。能用确定性评分的地方，就不要用模型评分。

## 跑几遍才够

@figure assets/course/ch20-evals.png 评测：同样的任务跑很多遍，两个版本成对比较，用区间而不是一个数说话

假设 B 版本真的比 A 好 10 个百分点。每个任务跑 3 遍，能看出来吗？用模拟代替真实模型，可以把这个问题看得很清楚：

@lab node labs/ch20/stats.ts

每个任务只跑 3 遍时，将近五分之一的实验会得出**相反的结论**——你会以为 B 更差，然后把一个好的改动撤回去。要可靠地看出 10 个百分点的差别，需要上百个样本。Pi 的 README 说得更直白：“一次重复不能证明稳定性”，默认每个变体只跑一次，要测稳定性就显式加 `--runs-per-variant`。

几个让结论更可靠的做法：

- **报告区间，而不是一个数。** 12 次里通过 9 次，真实的通过率可能在 47% 到 91% 之间（Wilson 区间，小样本时比常见的正态近似可靠）。24 次全过，下限也只有 86%：24 个样本证明不了“总是对的”。
- **成对比较。** 同一个任务、同一轮，两个变体各跑一次，只看结果不同的那些对。任务之间的难度差异被抵消了，比直接比较两个通过率更敏感。对结果不同的对数，还可以做个符号检验：4 对比 0 对，概率还有 12.5%，不够；8 对比 0 对，才是 0.8%。
- **交替顺序。** 奇数轮先跑 A，偶数轮先跑 B（上一节的 `createTaskPlan`），避免“总是先跑的那个”占便宜。
- **标出不稳定的任务。** 同一个变体时而通过时而失败的任务，最需要关注，也最容易误导结论（Pi 的 `flaky` 旗）。
- **不要只看通过率。** 成本（token）、耗时、轮数同样是指标：一个通过率高 2 个百分点、成本翻倍的改动，未必值得。

## 一次真实的 A/B 评测

用真实模型跑八个任务，比较两个变体：A 是 MiniMax-M3.1-Flash，B 是 MiniMax-M3，mox 的配置和提示完全一样，只换 `MOX_MODEL`。每个任务每个变体 3 轮，一共 48 次真正的 `mox -p` 运行，并发 3，用了 14 分钟。运行结果存档在 `labs/ch20/recorded/live-eval-models.json`（录制命令是 `node labs/ch20/live-eval.ts models 3`），下面是回放：

@lab node labs/ch20/live.ts models

这次评测的结果本身就是一课。Pi 的报告会给它标上三个旗：`no-lift`（通过率没有差别）、`control-saturated` 和 `treatment-saturated`（两边都是 100%）。具体看：

- **两个变体都是 24/24。** 八个任务，包括有隐藏边界情况的 `merge-intervals`、要求读规格的 `follow-spec`、测试本身是错的 `wrong-test`，两个模型每次都做对了，评测**看不出任何差别**。Pi 的评测报告专门会标出这种“饱和”的情况。即使是 24/24，95% 区间的下限也只有 86%：24 个样本证明不了“总是对的”。成对比较里，不同的对数是 0。
- **通过率一样，成本不一样。** B 的平均回合数更少（6.8 对 8.2），平均耗时是 A 的 0.8 倍，可是估算的输入 token 是 1.4 倍：每个回合发出去的历史更长。哪个“更好”取决于你付的是时间还是 token。
- **方差本身是发现。** 看回合数那张表：`answer-question`（“这个项目怎么运行测试？”）A 有一轮用了 14 个回合、两分钟，另外两轮只用了 3、4 个；`merge-intervals` A 的三轮是 7、18、6。同一个变体、同一个任务，成本相差好几倍。平均值把这个藏起来了，三个样本也不足以估计它。如果你关心的是“最坏情况多贵”，要看分布，不是均值。
- **验证率相近。** 改动了文件的运行里，最后一次修改之后又运行命令验证的，A 是 20/21，B 是 18/21。差别在噪声里。

所以这次评测的结论不是“M3 没用”，也不是“Flash 够用”，而是“这组任务回答不了‘换模型是否变好’”。下一步应该加入更难的任务（多个文件、需要先读懂代码才能修的 bug、很长的任务），让基线不再是 100%，再比较两个变体。设计评测任务时，先确认基线的通过率落在中间区域，评测才有区分能力。

还有一件事没有在表里：`follow-spec` 的 A 变体有一轮**运行出错之后重跑**了两次，才拿到有效结果。出错的原因是模型服务的限流（调试时同一批任务并发更高，满屏都是 429：请求太频繁）；mox 不重试，运行直接失败。如果把它们当成任务失败，A 的通过率就被无辜地拉低了；框架把它们标成无效观测，等一会儿、重跑一次全新的运行。这是第 21 章练习里“给 mox 加重试”的由来。

## 轨迹：怎么失败的

通过率告诉你**有多少**失败，轨迹告诉你**怎么**失败。一次运行的轨迹就是它的全部消息（第 7 章的会话记录）。Pi 的评测把每个运行的原生 `session.jsonl` 都存下来，从中可以提取出很多有用的信号：

- **重复的调用**：一模一样的工具调用出现了好几次，常常意味着在原地打转。
- **工具出错的次数**：模型是不是在和工具的参数格式较劲（第 4 章）。
- **最后一次修改之后有没有验证**：上面的评测正是用它来看模型有没有养成“改完就跑一遍”的习惯。
- **token 和缓存命中**：成本异常时先看这里（第 6 章）。

在线上运行的 Agent 里，同样的信息以遥测（telemetry）的形式收集：每次模型请求、每次工具调用都是一个带时间和属性的“跨度”（span）。Pi 的 `telemetry` 包定义了一套不绑定具体后端的接口，可以接到 OpenTelemetry 之类的系统上。评测和遥测是一体两面：评测在上线前回答“变好了吗”，遥测在上线后回答“现在怎么样”，而线上发现的失败，又应该变成新的评测任务。

::: note 公开的基准测试
SWE-bench（修复真实开源项目的 issue）、Terminal-Bench（在终端里完成任务）这类公开基准，衡量的是“模型 + Agent 框架”这个整体。它们适合横向比较，但离你自己的使用场景往往很远，还可能有训练数据污染的问题。真正指导你改进的，是一套贴近自己工作的小评测。
:::

## 实战：给 mox 做评测

**目标。** 做一套评测 mox 的最小框架：每次运行真正的 `mox -p "任务" --yolo`，在一个全新的目录和全新的 HOME 里，按最终状态评分，重复、对比、读轨迹。它比 Pi 的评测小得多（没有容器，没有 Vitest），但“全新环境、隐藏测试、成对、无效观测单独算”这些原则一样不少。产出在 `evals/`：`harness.ts`、`cases.ts`、`trajectory.ts`。

???
失败，原因是“改动了不该改的文件：README.md、notes.txt”。评分用的是 `git status --porcelain`，新建但没有提交的文件也在输出里（`?? notes.txt`），所以“改了哪些文件”包含新文件。这正是用 git 做基线的好处：布置现场时提交了一次，之后任何偏离，不管是改了、删了还是新建了，都看得见。在 `labs/ch20/validate.ts` 里给 `stay-in-scope` 加一个“顺手建文件”的投机版本，就能验证（评分器要把它判为失败）。

::: predict 差距变大，样本能少一点吗？
把 `labs/ch20/stats.ts` 里的 B 改成 `[0.95, 0.95, 0.95, 0.95]`（平均通过率 95%，对 A 的 72.5% 高出 22.5 个百分点），每个任务跑 3 遍的行会变成什么？
???
“看出 B 更好”约 91%，“看不出差别”约 7%，“结论反了”约 2%（原来是 64%、18%、18%）。差距越大，需要的样本越少：22.5 个百分点时，每个任务跑 3 遍（每个变体 12 个样本）已经能在九成的实验里看出来；跑 10 遍（40 个样本）就是 100%。但要小心反过来的结论：你真正关心的改动，往往只有几个百分点的差别，需要的样本量是这里的几倍到几十倍。
:::

::: predict 评测要不要一个不重跑的版本？
把 `labs/ch20/live-eval.ts` 里的 `retries: 3` 去掉，并发调到 8，在同一个模型服务上再跑一遍。通过率会变吗？报告会怎么写？
???
通过率本身不会变，但“有效观测”会变少。并发高了，模型服务开始返回 429；mox 不重试，那几次运行直接失败，记成“运行出错”，不进入通过率，也不进入成对比较——变体 B 的某一轮出错了，A 的同一轮就配不成对。报告头部会写“另有 N 次运行出错，不计入通过率”，N 越大，结论越不可靠：Pi 的报告里，任何一对结果不完整，就不给出总的结论。如果你把这些出错的运行当成“失败”算进通过率，两个变体的通过率会被限流的运气拉低，而不是被模型的好坏拉低。
:::

练习：给框架加一个“任务难度诊断”：跑完之后，把两个变体都 100% 通过的任务标出来（对应 Pi 的 saturated 旗），建议先删掉或加难；再写第九个任务，让它在 Flash 上通过率落在 30%～70%。

## 面试题

先自己回答，再展开对照要点。

::: interview 你怎么知道对 Agent 的一个改动（提示词、工具、模型）是变好了还是变坏了？
用评测：一组贴近真实使用的任务，每个任务在隔离的环境里运行，用确定性的方式评分（看最终状态，用隐藏测试），两个版本成对地、交替顺序地多次运行。报告通过率及其置信区间、成对比较中结果不同的对数、不稳定的任务，同时看成本、耗时和轮数。运行出错的观测单独统计、重跑，不算失败。样本太少时不下结论。改动上线后，用遥测和线上的失败案例继续补充评测集。
:::

::: interview 怎样为 coding agent 设计评分器？
- 看最终状态而不是模型的说法：运行测试、检查文件、检查 git 改动范围。
- 用隐藏测试，防止 Agent 迎合可见的测试或修改测试。
- 检查“不该发生的事”：改动了无关文件、删除了测试、引入了新的依赖。
- 先用已知答案的样本验证评分器：正确的必须通过，敷衍的、投机的必须失败。
- 区分“运行出错”和“任务失败”。
- 开放式任务才用模型评分，并给出评分标准、用人工标注校准。
:::

::: interview LLM-as-judge 有什么问题？怎么用好它？
问题：评分本身有随机性；有系统性的偏好（偏爱更长、更自信、和自己风格相近的回答，受位置影响）；可能被被评的内容影响（注入）。用法：给出明确、可操作的评分标准和示例；比较式（A 和 B 哪个好）通常比打绝对分数稳定，并交换顺序各评一次；用一批人工标注的样本测它和人的一致程度；能用确定性评分的部分就不交给模型。
:::

::: interview 评测需要跑多少次？两个版本的结果怎么比较？
取决于你想看出多大的差别：要可靠地分辨 10 个百分点的差距，每个变体需要上百个样本；只跑几次时，经常会得出相反的结论。比较时用成对的设计（同一任务同一轮各跑一次，只看结果不同的对），交替运行顺序，报告置信区间而不是单个百分比，并标出不稳定的任务。还要同时比较成本和耗时。
:::

::: interview 评测集会“过拟合”吗？
会。反复针对同一组任务调整提示词，最后得到的是“在这几个任务上表现好”的提示词。缓解办法：留一部分任务只用来做最终确认，不参与调整；持续从真实使用中加入新任务（尤其是线上失败的案例）；关注改动的原因是否通用，而不只是分数是否上升。
:::
