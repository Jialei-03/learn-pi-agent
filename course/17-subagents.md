## 一个干净的上下文

@figure assets/course/ch17-subagents.png 子 Agent：带着一张任务单进去，在里面翻遍资料，只带一张结论出来

问 Agent “压缩时从哪里切开对话？”，它会去翻 `compaction.ts`、`session.ts`、`loop.ts`，读进来两万多个字符。得到答案只需要其中三行，可剩下的内容会一直留在上下文里：之后的每一次请求都要带着它们，花钱、占空间、分散注意力（第 6、8 章）。

**子 Agent** 的做法是：把调研交给另一个 Agent 循环。它从空白的上下文开始，读文件、跑命令，最后只把结论交回来。读过的文件留在子 Agent 那里，随它一起丢掉。

子 Agent 解决三个问题：

- **上下文隔离**：“需要翻很多东西，但只要一个结论”的工作，不污染主对话。
- **专门化**：子 Agent 可以有自己的系统提示、工具集，甚至更便宜的模型（调研用小模型就够了）。
- **并行**：互不依赖的子任务同时进行。

把它和前面几种机制放在一起看：

| 机制 | 方向 | 时机 |
| --- | --- | --- |
| Skill（第 11 章） | 把知识**拉进**上下文 | 需要时 |
| 压缩（第 8 章） | 把旧内容**压小** | 快满时，事后 |
| 子 Agent | 把工作**推出**上下文 | 事前：知道这件事会产生大量中间内容 |

## 交接：任务说明和结论

子 Agent 看不到主对话，**父 Agent 写的任务说明是它唯一的上下文**。“查一下那个 bug”对子 Agent 毫无意义——哪个 bug？已经排除了什么？要返回什么？mox 的 `agent` 工具在描述里把这一点写给了模型：

返回的方向同样要设计。Pi 示例里的 scout（侦察）子 Agent，它的系统提示几乎全是在规定**输出格式**：读过哪些文件的哪几行、关键的类型和函数、模块之间怎么连接、从哪里开始看——因为它的输出要交给一个“没有看过这些文件的 Agent”：

父 Agent 拿到的只是子 Agent 的**最后一条回答**：

@pi packages/coding-agent/examples/extensions/subagent/index.ts#getFinalOutput

同一个问题，主 Agent 自己读，和交给 explore 子 Agent，对比一下上下文和总花费（读的是本仓库 mox 的真实源码，模型是脚本）：

@lab node labs/ch17/context.ts

两个数字都要看：

- 主对话的上下文从两万多字符降到不到一千。这才是重点：方案 A 读进来的两万字符会跟着之后的**每一次**请求，对话越长，省得越多。
- **总花费反而增加了。** 子 Agent 要重新付一遍系统提示和工具定义的钱，主 Agent 也多了一轮。子 Agent 是在用 token 换上下文。

所以简单的事（一两次工具调用就能完成）不该交给子 Agent，开销比省下的多。

## 两种实现

### Pi 的示例：独立进程

Pi 的子 Agent 示例为每个子 Agent 启动一个新的 `pi` 进程，用 JSON 模式输出事件、不保存会话，通过命令行参数指定模型和工具：

@pi packages/coding-agent/examples/extensions/subagent/index.ts#L298-L305

父进程逐行解析子进程 stdout 上的事件（和第 12 章 MCP 的 stdio 一样是“一行一条 JSON”），从 `message_end` 事件里收集消息、累计用量，实时更新界面。

### mox：同一进程里的新循环

mox 的做法是在同一个进程里再跑一次第 3 章的 `runLoop`，只是换了历史（空的）、系统提示和工具集：

@code mox/src/subagent.ts#runSubagent

| | 独立进程（Pi 示例） | 进程内（mox、Claude Code） |
| --- | --- | --- |
| 启动 | 慢：每次启动一个完整的 CLI | 快：几乎没有开销 |
| 隔离 | 崩溃、内存泄漏不影响父进程 | 共享进程 |
| 取消 | 杀进程，可靠 | 靠 AbortSignal 层层传递 |
| 共享 | 要通过参数传配置；钩子、权限扩展要在子进程里重新加载 | 直接共享模型客户端、钩子、权限规则 |
| 观察 | 解析事件流 | 直接订阅事件 |

## 并行、取消、权限、嵌套

@lab node labs/ch17/parallel.ts

**并发上限。** 四个任务、最多同时两个，分两波完成；结果按任务顺序排列，不按完成顺序。上限不只是为了省资源：模型服务商有速率限制，八个子 Agent 同时请求，很可能一起收到 429。

@code mox/src/subagent.ts#mapWithLimit

**取消。** 父 Agent 的 `AbortSignal` 传给每个子 Agent 的循环，再传给模型请求和工具（第 3、5 章）。用户按下 Ctrl+C，子 Agent 正在跑的命令也会被终止，0.3 秒就返回了。

**权限继承。** 子 Agent 的工具调用经过父 Agent 同一组钩子，第 14 章的权限规则照样生效。没有这一条，子 Agent 就成了绕过权限的后门：模型只要说“让子 Agent 去 rm -rf”就行了。

**嵌套。** mox 的子 Agent 拿不到 `agent` 工具，只能有一层。不限制的话，子 Agent 可以再派子 Agent，递归失控时，花费成倍增长。Claude Code 允许最多三层，可以配置。

**工具子集。** explore 只拿到 `read` 和 `bash`。但要注意：它的“只读”只是靠系统提示和工具选择，`bash` 照样能写文件。真正的只读需要给子 Agent 一个更严格的权限模式（第 14 章的 plan 模式）。Claude Code 的子 Agent 定义里就有 `permissionMode` 字段。

## 真实模型怎么用子 Agent

在本仓库里运行 mox，用真实模型问同一个问题：

@include labs/ch17/recorded/live-run.txt

模型按要求把调研交给了 explore，子 Agent 交回了一份详细的结论。然后主 Agent **又自己读了一遍** `compaction.ts` 和 `cli.ts` 来核实（“已核实”）。

这暴露了子 Agent 的一个根本问题：**信任**。子 Agent 的结论可能是错的（它可能读漏了，也可能被它读到的内容误导），父 Agent 无法判断，只好自己再看一遍——可这样一来，子 Agent 省下的上下文又被花掉了。

几种缓解的办法：

- 让子 Agent 返回**可核查的线索**（文件和行号，就像这次的结论那样），父 Agent 只需要看关键的几行，而不是整份文件；
- 在系统提示里说明子 Agent 的可靠性和定位，给出“什么时候需要核实”的标准；
- 对于父 Agent 必须亲自确认的事（比如马上要修改的代码），一开始就不要外包。

子 Agent 的结论还是**数据**，不是指令。它读过的网页、文件可能藏着注入（第 1 章），被它原样转述进了结论。Claude Code 会在父 Agent 读之前扫描子 Agent 的报告。

## 定义自己的子 Agent

mox、Pi、Claude Code 用的是同样的格式：一个 Markdown 文件，元信息里写名字、描述、工具，正文是系统提示。

```markdown
---
name: test-runner
description: 运行测试并分析失败原因。修改代码之后、或用户要求跑测试时使用。只返回失败的测试和最可能的原因。
tools: read, bash
---

你负责运行测试。先运行全部测试，对每个失败的测试：读出错的断言和相关代码，给出最可能的原因……
```

放在 `~/.mox/agents/` 下。和 Skill 一样，**描述决定了父 Agent 什么时候会想到用它**（第 11 章）。也和 Skill 一样，项目里的子 Agent 定义是仓库控制的提示，可以指示模型执行命令，所以 mox 只在 `--trust` 时加载 `.mox/agents/`，Pi 的示例默认只加载用户目录下的定义。

::: compare Claude Code 的子 Agent
- 内置 Explore（只读调研）、Plan（计划模式下的调研）、general-purpose 等；自定义的放在 `.claude/agents/` 或 `~/.claude/agents/`。
- 定义里可以指定 `tools` / `disallowedTools`、`model`（调研可以用便宜的模型）、`permissionMode`、`maxTurns`、要预先加载的 Skill、专属的 MCP 服务器和钩子、`isolation: worktree`（在独立的 git 工作树里运行，并行修改不冲突）。
- 子 Agent 默认从空白上下文开始，看不到主对话；它会加载 CLAUDE.md。还有一种 fork 模式，继承主对话的全部上下文——复用父 Agent 的提示前缀，提示缓存可以命中。
- 可以在后台运行，结果完成后通知；可以用 SendMessage 继续一个已经结束的子 Agent，它保留着自己的历史。
- 默认最多三层嵌套、同时 20 个。子 Agent 继承父 Agent 的权限规则。

官方文档：[Subagents](https://code.claude.com/docs/en/sub-agents)
:::

## 面试题

先自己回答，再展开对照要点。

::: interview 什么时候应该用子 Agent？什么时候不应该？
应该：需要读大量材料但只要结论的调研（找代码、查日志、读文档）；可以独立完成、做完汇报即可的子任务；互不依赖、可以并行的多个任务；需要不同系统提示、工具或更便宜模型的专门工作。

不应该：一两次工具调用就能完成的事（开销大于收益）；父 Agent 马上要亲自修改的代码（还得自己再读一遍）；需要大量来回沟通、依赖主对话上下文的工作；多个子 Agent 会修改同一批文件的情况（除非用独立的工作树隔离）。
:::

::: interview 子 Agent 的输入和输出怎么设计？
输入：子 Agent 只能看到任务说明，所以要写清楚背景、目标、已知和已排除的信息、约束、要返回什么（格式和详细程度）。工具描述里要把这些要求告诉父 Agent。

输出：只交回最后的结论，并限制长度。结论要能被一个没看过原始材料的 Agent 直接使用：给出精确的位置（文件、行号）以便核查，区分事实和推测，不要复述大段原文。子 Agent 的输出是数据，不是指令。
:::

::: interview 子 Agent 应该在独立进程里运行，还是在同一个进程里？
独立进程：隔离好（崩溃、内存互不影响），取消可靠（杀进程），可以使用不同的配置；但启动慢，配置、钩子、权限要重新加载，通信要靠序列化的事件流。

同一进程：启动快，直接共享模型客户端、权限规则、钩子和事件；但共享进程资源，取消要靠信号层层传递，一个失控的子 Agent 可能影响父 Agent。Claude Code 和 mox 选择进程内，Pi 的示例选择独立进程。需要更强隔离（比如修改代码）时，可以再加一层：独立的 git 工作树、沙箱或容器。
:::

::: interview 多个 Agent 并行工作，会遇到哪些问题？
- 速率限制与费用：要有并发上限，总花费随 Agent 数量增长。
- 文件冲突：多个 Agent 修改同一批文件。办法是按文件划分任务、用独立的 git 工作树、或只让一个 Agent 写。
- 结果汇总：按任务顺序返回；部分失败时，失败的要明确标出，不能静默丢掉。
- 取消与清理：父 Agent 取消时，所有子 Agent 都要停下，包括它们启动的进程。
- 权限：子 Agent 必须继承同样的权限限制，不能成为绕过审批的通道。
- 递归：限制嵌套深度和总数量。
:::

::: interview 子 Agent 交回的结论，父 Agent 应该相信吗？
不能完全相信。子 Agent 可能读漏、误解，也可能被它读到的内容（网页、文件里的注入）误导。可是父 Agent 如果全部重新核实，子 Agent 就白用了。折中的办法是让子 Agent 返回可核查的证据（精确的文件和行号、原始的错误信息），父 Agent 只核查关键的部分；对必须亲自确认的事（马上要改的代码），一开始就不要外包；并且始终把子 Agent 的输出当作数据而不是指令。
:::
