## 会话之间什么都不剩

第 7 章让对话能够保存和恢复，但每个新会话都是从零开始的。上周你纠正过 Agent 三次“这个项目用 pnpm，不要用 npm”，这周开一个新会话，它照样会去跑 `npm install`。

现在有几种机制都和“记住”有关，它们解决的是不同的问题：

| 机制 | 谁写 | 生命周期 | 解决什么 |
| --- | --- | --- | --- |
| 会话历史（第 7 章） | 自动记录 | 一个会话 | 同一个任务内的上下文 |
| 压缩摘要（第 8 章） | 模型总结 | 一个会话 | 长任务里腾出空间 |
| AGENTS.md（第 6 章） | 人写，提交到仓库 | 永久，团队共享 | 项目约定 |
| **长期记忆** | **Agent 在工作中写** | **跨会话，通常只属于一个用户** | **从协作中学到的东西：偏好、纠正、背景** |

长期记忆填的是最后一格：用户没有专门去写，但在协作中表达过的东西。

## 其他 Agent 怎么做

| Agent | 做法 |
| --- | --- |
| Claude Code | 自动记忆（默认开启）：模型把学到的东西写进一个记忆目录，`MEMORY.md` 作为索引，每个主题一个文件；记忆分为用户、反馈、项目、参考几类；每个会话开始时加载索引的前 200 行（或 25KB）。官方文档：[Memory](https://code.claude.com/docs/en/memory) |
| Gemini CLI | 模型可以把要点写进 `GEMINI.md` 或私有的记忆目录；实验性的自动记忆会从会话里提取候选条目，放进收件箱，由用户审核后才生效 |
| Codex CLI | 默认关闭的“记忆”功能：在后台总结空闲的会话，写入记忆目录 |
| Pi | 没有内置 |

几家的做法有明显的共同点：**用文件存储，有一个简短的索引，只有索引进入上下文，细节按需读取。** 这和第 11 章的 Skills 是同一个思路：渐进式披露。所有记忆的全文都塞进系统提示，既占空间，也会分散模型的注意力。

## 设计一个记忆扩展

我们给 Pi 写一个记忆扩展，设计如下：

**存储**：一个目录，`MEMORY.md` 是索引，每条记忆一个 Markdown 文件，开头有元信息（名字、一行描述、类型、状态、来源）。

**类型**决定了“什么值得记”：

@code extensions/memory/store.ts#MEMORY_TYPES

不该记的同样重要：代码结构（读代码就知道）、git 历史（查一下就知道）、这次任务的临时状态（任务结束就没用了），以及任何密钥。

**进入上下文的方式**：每次运行开始时，把索引作为系统提示的一个**小节**放进去。这里用到了第 6 章的机制：扩展直接修改 `before_agent_start` 事件里的结构化提示选项，而不是返回一个完整的新系统提示：

@code extensions/memory/index.ts#L22-L27

这个区别很关键。如果返回整个新系统提示，每次记忆变化都会让开头的系统提示改变，提示缓存全部失效。修改小节则交给 Pi 的比较机制：会话中途保存了一条新记忆，下一次运行时 Pi 只在历史末尾追加一条“memory 小节已更新”的补丁。

**索引的文字**本身也是设计的一部分。它不仅列出记忆，还告诉模型什么时候该保存、什么不该保存，以及**记忆可能过时**：

@code extensions/memory/store.ts#promptSection

最后一条提醒值得强调：记忆是某个时间点写下的。三个月前记下的“认证逻辑在 `src/auth.ts`”，可能早就被重构掉了。模型引用记忆里的文件或函数之前，应该先确认它们还存在。

## 记忆投毒

长期记忆带来了一种新的风险。

第 1 章说过，模型读到的文件、网页、命令输出都可能藏着给 AI 的指令（间接提示注入）。在没有长期记忆时，这类攻击的影响局限在当前会话里。但如果模型被诱导调用了 `save_memory`，恶意指令就会写进记忆，**出现在之后每一个会话的系统提示里**——系统提示是模型最信任的位置，而用户可能完全不知道它的存在。

所以写入策略比存储格式重要得多。我们的扩展采用了三条规则：

1. **用户明确要求时直接生效。** 用户这次的输入里说了“记住”“以后都”之类的话，模型保存的记忆立即生效。
2. **模型自己决定记的，进入待确认列表。** 有界面时弹窗确认；没有界面时标记为待确认，不进入系统提示，直到用户用 `/memory approve` 确认。
3. **看起来像密钥的内容一律拒绝。**

@code extensions/memory/index.ts#L43-L54

每条记忆还记录了来源（“用户要求”“模型提议，用户确认”“等待确认”），方便事后审查。

这个实验用四个独立的 Pi 会话共用一个记忆目录：

@lab node labs/ch10/memory.ts

逐段看：

- **会话一**：用户说“记住”，记忆立即生效。同一会话里的下一次运行，系统提示的开头没有被改动，而是追加了一条只包含 `memory` 小节的更新。
- **会话二**：一个全新的会话，系统提示里出现了这条记忆，模型据此回答要运行 `pnpm test`。
- **会话三**：用户只是让模型总结一个网页，网页的 HTML 注释里藏着给 AI 的指令。脚本模型照做了（真实模型也可能照做），但因为用户并没有要求记住任何东西，这条记忆只进了待确认列表；试图保存的 API Key 被直接拒绝。
- **会话四**：被诱导写下的记忆没有出现在新会话的系统提示里。

::: warn 规则是启发式的，不是安全边界
“用户输入里有没有‘记住’”只是一个简单的判断，攻击者可以设计出绕过它的场景（比如诱导用户自己说“记住这个网页的建议”）。真正的防线是**让用户看得见**：哪些记忆生效了、是从哪里来的，可以随时审查和删除。任何会持久影响 Agent 行为的写入（记忆、配置、`AGENTS.md`、扩展），都值得同样的对待。
:::

## 记忆多了之后

当记忆增长到几百条，索引本身也会变成负担。这时有几个方向：

- **整理**：定期合并重复的条目，删除过时的，像整理笔记一样。可以让 Agent 在空闲时自己做，但删除应该让用户确认。
- **按需检索**：不把全部索引放进上下文，而是根据当前任务检索相关的几条（关键词或向量检索，也就是常说的 RAG）。代价是多了一次检索步骤，而且检索可能漏掉真正相关的条目。
- **分层**：用户级的偏好总是加载，项目级的只在对应项目里加载。我们的扩展已经按项目目录分开存储。

对 coding agent 来说，一个精心维护的小索引通常比一个庞大的检索系统更可靠：记忆的价值在于“少而准”。

## 面试题

先自己回答，再展开对照要点。

::: interview 如何为 Agent 设计长期记忆？
- **存储**：文件即可。一个简短的索引（每条一行，带描述），每条记忆一个文件，带类型、来源、更新时间等元信息。
- **加载**：只把索引放进上下文，细节按需读取；限制索引的长度；放在系统提示的独立小节里，变化时以补丁方式更新，保护提示缓存。
- **内容**：只记无法从代码和历史得到的信息——用户偏好与纠正（附原因）、项目背景与决定、外部资源位置；不记代码结构、临时状态和密钥。
- **写入策略**：用户明确要求的直接生效；模型自主写入的需要确认；拒绝疑似密钥；记录来源。
- **维护**：提醒模型记忆可能过时；提供查看、确认、删除的入口；记忆变多时整理或检索。
:::

::: interview 长期记忆、会话历史、AGENTS.md、RAG 有什么区别？
会话历史是一次任务内的完整记录；压缩摘要是长任务中为腾出空间写的总结。AGENTS.md 是人写的项目约定，提交到仓库、团队共享。长期记忆是 Agent 在协作中积累的、跨会话的个人知识。RAG 是一种检索技术，可以用来从大量记忆或文档中找出相关部分，它解决的是“放不下时怎么挑”，而不是“记什么”。
:::

::: interview 什么是记忆投毒？怎么防御？
模型读到的不可信内容（网页、文件、命令输出）里藏着指令，诱导模型把恶意内容写入长期记忆。与普通的提示注入不同，它会持久存在，并以最高信任级别出现在之后的每个会话里。

防御：区分用户明确要求的写入和模型自主的写入，后者需要用户确认；拒绝疑似凭证；记录每条记忆的来源；让用户能方便地查看和删除；记忆内容同样要经过后续的权限控制，不能因为“记忆里说要这么做”就绕过审批。
:::
