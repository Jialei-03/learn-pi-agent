# 从大模型到 Agent：模型、宿主与运行循环

> **本章问题：一个能够回答问题的大模型，为什么还不能独立完成一个任务？**

“给大模型接上工具，它就变成了 Agent”这句话描述了一个现象，却没有说明最重要的工程边界：**模型负责生成，宿主程序负责组织、校验和执行**。

本章只建立一条基础主线：

```text
用户输入 → 宿主准备上下文 → 模型生成响应
                         ↓
              文本回答，或 Tool Call
                         ↓
              宿主执行、回填、继续或停止
```

本章暂不展开 OpenAI、Anthropic 的具体 JSON，也不直接阅读 Pi 的源码目录。先把模型、消息、上下文、运行状态和循环之间的关系分清楚，后面进入 API 与源码时才不会把不同层次混在一起。

## 1. 先划清边界：模型不会执行动作

### 1.1 一次普通模型调用

把 SDK 和网络细节拿掉，一次基于消息的模型调用可以用下面的教学伪代码表示：

```ts
type Message = {
  role: "system" | "user" | "assistant" | "tool";
  content: string;
};

const messages: Message[] = [
  { role: "user", content: "法国的首都是什么？" },
];

const response = await model.generate(messages); // 教学伪接口
```

这里故意只展示最小的文本消息。真实 API 还要表达内容块、工具调用和工具结果，具体字段留到下一章比较。

这段代码表达的是一个请求—响应边界：

1. 宿主程序准备本次请求的消息；
2. 模型服务根据输入生成响应；
3. 宿主程序收到响应，并决定展示、保存或继续处理。

如果模型返回“巴黎”，这次调用就可以结束。模型生成了内容，但它没有因此获得读取文件、发送网络请求或修改数据库的权限。

![一次模型调用与一个 Agent 运行过程的差别](../../assets/from-llm-to-agent-illustrations/01-model-vs-agent.png)

### 1.2 文本响应不会自己变成动作

模型可以生成一句“我已经读取了 `README.md`”。如果宿主程序没有注册读文件工具，这句话仍然只是文本。模型 API 不会因为响应中出现“读取”“运行”或“发送”这些动词，就自动越过宿主环境的权限边界。

可以先记住这条边界：

```text
模型可以提出下一步；宿主程序决定下一步能不能发生。
```

| 能力 | 模型 | 宿主程序 |
| --- | --- | --- |
| 根据输入生成文本或结构化请求 | ✓ | 可以转发，但不负责推理 |
| 选择一个工具并提出参数 | ✓ | 可以校验和拒绝 |
| 读取文件、调用网络、执行命令 | 不能直接执行 | 可以执行，但要受策略控制 |
| 保存会话、处理取消和超时 | 不负责 | 负责 |

这不是说模型“不重要”，而是说明它在系统中的位置：模型是决策和生成组件，Agent 是围绕模型运行的整个系统。

## 2. Message、Context、State、Session 不是同一个东西

Agent 初学者最容易把“历史”“记忆”“上下文”和“状态”当成同义词。它们在工程上承担不同职责。

### 2.1 Message：一次交互中的记录

`Message` 是一条交互记录，通常包含发送者角色和内容。内容不一定是纯文本，也可以是图片、工具调用请求或工具结果。

不同供应商的角色名称和内容块字段并不完全相同，但它们都需要表达类似事实：

```text
谁产生了这条内容？
内容是什么？
它是否与某一次工具调用相关？
```

因此，Message 是一个记录单位，不是整个对话，也不是模型的永久记忆。

### 2.2 Context：本轮真正发给模型的输入

`Context` 是宿主程序为某一次模型调用准备的输入快照。它可能包括：

- 系统提示和行为规则；
- 当前用户消息与部分历史；
- 工具定义和输入 schema；
- 项目文件摘要、检索结果或其他资源；
- 本轮可暴露给模型的能力说明、token 和输出约束。

模型只能依据本轮收到的 Context 工作。保存了完整历史，不代表所有历史都会进入本轮 Context；Context 还受到窗口容量、成本、延迟和选择策略的限制。

### 2.3 State：运行时的全部状态

`State` 的范围比 Context 更大。一个运行中的 Agent 可能需要保存：

- 消息历史和当前模型；
- 工具注册表与权限策略；
- 正在执行的工具调用；
- 取消信号、错误、重试次数和停止原因；
- token 使用量、事件订阅者和会话标识。

其中有些状态需要发给模型，有些状态只供宿主程序使用。例如，取消信号和权限策略不应该直接变成模型可以修改的指令。

可以用一个工程化的近似表示它们的关系：

```text
Context_t = project(State_t, selection_policy_t)
```

意思是：第 `t` 次调用的上下文，是宿主根据当前状态和选择策略投影出来的一部分输入，而不是全部运行状态。

### 2.4 Session：跨多个 turn 保存的会话记录

`Session` 通常表示跨多个 turn 持久化的消息、元数据和分支信息。它可以落盘、恢复、分支或压缩，但它仍然属于宿主系统管理的记录。

| 对象 | 关注的问题 | 生命周期 | 是否必然发给模型 |
| --- | --- | --- | --- |
| Message | 这一条内容是谁产生的 | 一条记录 | 只有被选入 Context 才会 |
| Context | 这次调用让模型看到什么 | 一次模型调用 | 是 |
| State | 系统现在进行到哪里 | 一次运行或多个 turn | 否 |
| Session | 怎样保存和恢复一段会话 | 跨运行 | 否 |

所以，“Session 保存了历史”不等于“模型永久记住了历史”，而“历史进入了 Context”也不等于“模型会同等可靠地使用每一段信息”。

## 3. Agent Loop：从一次响应到多轮运行

Agent 的关键不在于模型输出了某个特殊词，而在于宿主程序会不会根据响应继续运行。

### 3.1 模型响应至少有两种语义

为了暂时避开供应商字段差异，可以使用一个教学类型表达共同语义：

```ts
type ModelResponse =
  | { kind: "text"; text: string }
  | {
      kind: "tool_call";
      id: string;
      name: string;
      arguments: unknown;
    };
```

真实 API 会使用不同的字段和内容块，但从 Agent Loop 的角度看，宿主首先要判断：

- 这是可以展示或结束的文本响应；
- 还是需要宿主处理的工具调用请求。

`Tool Call` 只表示“模型请求宿主考虑调用某个工具”，不表示工具已经执行。

### 3.2 一个最小但边界清楚的循环

下面的代码仍然是教学伪代码，但它把执行边界、参数校验和结果回填放在了正确的位置：

```ts
async function runAgent(state: RuntimeState) {
  for (;;) {
    const context = projectContext(state);
    const response = await model.generate(context);

    appendAssistantResponse(state, response);

    if (response.kind === "text") {
      return response.text;
    }

    const tool = registry.get(response.name);
    if (!tool) {
      appendToolError(state, response.id, "unknown_tool");
      continue;
    }

    const args = validate(response.arguments, tool.schema);
    if (!args.ok || !policy.allows(tool, args.value)) {
      appendToolError(state, response.id, "rejected");
      continue;
    }

    const result = await tool.execute(args.value, runtime);
    appendToolResult(state, response.id, result);
  }
}
```

这里的 `RuntimeState`、`registry` 和 `policy` 都是教学伪类型；真实实现还要把最大轮次、取消信号、超时和错误处理接入循环。

这段循环的控制顺序是：

1. 从运行状态投影本轮 Context；
2. 调用模型；
3. 保存模型响应；
4. 文本响应直接结束，Tool Call 则进入宿主处理；
5. 检查工具是否存在、参数是否合格、策略是否允许；
6. 执行工具，把结果和原始调用的 `id` 关联后写回状态；
7. 回到下一轮。

### 3.3 这个循环必须保持的边界

一个可运行的 Agent Loop 至少要保证下面几件事：

- **模型提出请求，宿主执行动作。** 模型不能跳过工具注册表和权限策略。
- **Tool Call 与 Tool Result 一一关联。** 多个并行调用时，结果不能靠顺序猜测。
- **每一轮都重新准备 Context。** 工具结果、用户追加指令和状态变化必须有机会进入下一次调用。
- **宿主决定何时停止。** 可以因为最终文本、错误、取消、超时、最大轮次或策略拒绝而停止。
- **副作用位于执行边界。** 网络、文件和命令等动作必须由宿主控制，而不是由模型文本直接触发。

## 4. 用一次天气请求走完整条链路

现在把抽象循环落到一个具体例子。用户问：“北京现在天气怎么样？”模型的训练知识不能保证提供实时天气，宿主因此注册了一个 `get_weather` 工具。

![从用户问题到工具结果再到最终回答的完整闭环](../../assets/from-llm-to-agent-illustrations/02-tool-call-loop.png)

### 第一步：宿主准备初始 Context

宿主把用户问题、必要的系统规则和工具定义放进本轮 Context。模型看到的是工具的结构化描述，而不是宿主进程中的 JavaScript 函数本体：

```text
工具名：get_weather
用途：查询某个城市的当前天气
输入：{ city: string }
```

工具定义告诉模型“可以请求什么”，但不把真实执行权交给模型。

### 第二步：模型返回 Tool Call

模型可能返回下面这种教学形状：

```json
{
  "id": "call_1",
  "name": "get_weather",
  "arguments": { "city": "北京" }
}
```

这不是 OpenAI 或 Anthropic 的完整 API 格式，只用来表示共同语义：模型提出了一个带调用标识和参数的请求。此时网络请求还没有发生。

### 第三步：宿主校验并决定是否执行

宿主至少要检查：

- `get_weather` 是否是已注册工具；
- `city` 是否符合输入 schema；
- 当前用户和运行环境是否允许调用；
- 调用是否超过超时、速率或成本限制。

校验通过后，宿主才调用真正的天气服务。校验失败时，宿主也可以生成一个错误结果，让模型知道这次请求没有执行成功。

### 第四步：宿主写回 Tool Result

假设天气服务返回：

```json
{
  "temperature": "28°C",
  "condition": "多云",
  "observed_at": "2026-08-16T10:00:00+08:00"
}
```

宿主需要把它包装成与 `call_1` 对应的 Tool Result，再加入运行状态。关联标识很重要：如果一轮有多个工具调用，模型必须知道每个结果回答的是哪一个请求。

### 第五步：模型生成最终回答或下一次请求

下一轮 Context 包含原始问题、Tool Call 和对应结果。模型可以据此生成：“北京当前 28°C，多云；观测时间为上午 10 点。”

如果结果不足以完成任务，模型也可能继续请求另一个工具。是否继续不是天气工具决定的，而是由下一次模型响应和宿主的停止策略共同决定的。

## 5. 为什么生产级 Agent 不只是几十行循环

上面的伪代码抓住了主干，但真实 Agent Harness（围绕模型、工具、状态和生命周期的运行编排层）还要处理三类工程问题。

### 5.1 控制问题：怎样可靠地停止

系统需要明确处理最大轮次、超时、取消、重试、用户中途追加指令和工具失败。没有停止条件的循环不是“更自主”，而是一个可能无限运行的故障。

### 5.2 数据问题：怎样保持消息和上下文正确

系统需要处理多个 Tool Call、流式响应、增量参数、调用标识、上下文窗口、token 预算、Session 持久化和 compaction。任何一项处理错误，都可能让模型看到不完整或错误关联的历史。

### 5.3 副作用问题：谁有权改变外部世界

文件写入、命令执行、网络请求和数据修改都可能造成副作用。Schema 只能检查输入形状，不能替代权限、沙箱、用户确认、路径边界和审计。

因此要始终记住两个边界：

```text
Tool Call ≠ 工具已经执行
Session ≠ 模型永久记住了历史
```

## 本章小结

- 模型负责根据 Context 生成文本或结构化请求，宿主程序负责组织运行和执行副作用；
- Message 是一条交互记录，Context 是本轮发送给模型的输入，State 是运行时状态，Session 是跨运行保存的会话记录；
- Agent Loop 通过“调用模型—处理 Tool Call—执行工具—回填结果—继续或停止”把一次响应变成多轮运行；
- Tool Call 不是执行结果，宿主必须负责注册、校验、授权、执行和关联 Tool Result；
- 生产级 Agent 的难点不只在循环，还在停止条件、数据一致性、权限和副作用控制。
