# 源码版本为什么重要

阅读正在快速发展的开源项目，最常见的挫折不是“代码太难”，而是文章和你眼前的代码根本不在同一个时间点。函数可能改名，目录可能迁移，原本串行的步骤可能增加并发，甚至一个包的职责也会重新划分。

因此，本仓库把**版本信息视为正文的一部分**。

## 两种“当前”不要混在一起

### 当前上游状态

指 Pi 官方仓库此刻默认分支所展示的内容。它适合了解最新能力、安装方式和维护状态，但会继续变化。

### 文章写作基线

指某篇讲解在查证源码时使用的确定 commit。首个版本统一使用：

```text
086c32e74530564922d011ade23ff582c9d63116
```

核对日期：**2026-08-16**。

固定基线不是认为这个版本“最好”，而是让作者和读者讨论同一份证据。即使 Pi 的 `main` 明天改变，带 commit 的链接仍会指向文章写作时实际阅读的文件。

## 为什么不要依赖历史行号

文章写“看第 132 行”看起来很精确，实际上很脆弱：文件前面增加一个 import，所有行号都可能变化。更可靠的定位方式是组合使用：

- 固定 commit 的文件链接；
- 稳定的类型名或函数名；
- 这个符号在调用链中的职责；
- 必要时附上当时的行号作为辅助，而不是唯一地址。

例如，与其只说“打开 `agent-loop.ts` 第 N 行”，更好的方式是：打开固定版本的 [`packages/agent/src/agent-loop.ts`](https://github.com/earendil-works/pi/blob/086c32e74530564922d011ade23ff582c9d63116/packages/agent/src/agent-loop.ts)，搜索 `runAgentLoop`，再观察它接收的状态、消息和工具配置。

## 看到差异时怎样判断

按这个顺序检查：

1. **确认仓库**：是否是 `earendil-works/pi`，而不是旧 fork 或同名项目；
2. **确认 commit**：浏览器 URL 中是否包含本文基线；
3. **搜索符号**：文件迁移时，类型名与调用方往往比路径更容易追踪；
4. **查看提交历史**：判断是重构、功能变化还是文章错误；
5. **记录两边证据**：报告问题时同时给出文章链接、基线 commit 与最新源码链接。

不要为了让文章“看起来最新”而默默把链接改到 `main`。如果行为已经发生实质变化，应新建或更新版本记录，并说明哪些结论仍成立、哪些需要重写。

## 外部 API 也需要核对日期

OpenAI、Anthropic 和 MCP 的接口同样会演进。API 章节会尽量链接官方文档，并记录最后核对日期。对于供应商接口，本仓库优先解释稳定语义，再展示具体字段：例如不同 API 都需要把工具请求与对应的工具结果关联起来，但字段名和内容块结构未必相同。

## 本仓库怎样记录基线

[版本基线](../../references/version-baseline.md)集中记录：

- Pi 上游仓库、固定 commit 与核对日期；
- 关键源码入口；
- OpenAI、Anthropic、MCP 等官方协议链接；
- 哪些内容属于易变信息；
- 升级基线时应执行的检查。

[源码地图](../../references/source-map.md)中的 Pi 链接也固定到同一 commit，避免一张地图同时混用多个时期的源码。

## 给未来自己的版本笔记

当你学习或写作时，建议保存下面四项：

```text
阅读日期：
仓库与 commit：
正在回答的问题：
关键符号与调用方向：
```

这四行比一堆没有上下文的代码截图更有价值。几个月后回看时，你仍然知道当时为什么打开这个文件、基于哪份源码得出了什么结论。
