# 短视频制作规范

## 1. 内容原则

每支视频只回答一个核心问题。开头先给出常见误解或真实困惑，中间通过一条清晰的因果链解释，结尾给出可以带走的判断标准，并自然引出下一章。

短视频可以压缩论证长度，不能压缩概念边界。尤其要保留以下区分：

- 模型生成与宿主执行；
- Tool Call 与 Tool Result；
- 模型的停止信号与 Runtime 的运行控制；
- Context、State、Session 与 Memory；
- 协议、SDK、Runtime、Harness 与产品界面；
- Policy、Approval 与 Sandbox；
- 输出质量与执行轨迹。

## 2. 画布与安全区

- 主画布：1080 × 1920，30 fps；
- 背景：暖白 `#F7F5F0`；
- 主文字：近黑 `#171717`；
- 强调色：Mox 橙 `#FF7A00`；
- 关键内容放在横向 72～1008、纵向 120～1530 的安全区；
- 字幕放在纵向 1580～1830，最多两行；
- 小红书原卡片是 1080 × 1440，可作为构图底稿，不直接铺满 9:16 画布。

## 3. 一张卡片怎样变成动画

每个镜头最多组合三类运动：

1. **结构进场**：标题、卡片、模块按阅读顺序出现；
2. **关系聚焦**：推近关键区域，或用橙色线条、括号、箭头强调因果；
3. **状态变化**：让请求变成结果、让循环指针移动、让状态机节点切换。

避免整页持续漂浮、无含义的粒子、频繁弹跳和逐字乱飞。动画必须帮助观众理解“谁把什么交给谁”或“状态如何变化”。

## 4. 节奏

- 封面 5～7 秒，先出现问题，再出现章节名；
- 普通知识卡 8～10 秒；
- 复杂关系图 10～13 秒，可先给整体，再聚焦局部；
- 转场 8～14 帧，以橙线擦除、纸张推移或镜头推近为主；
- 每次镜头切换前给口播留下约 0.15 秒呼吸空间。

分镜中的时间是录音前估算值。拿到真人录音后，以语义停顿重新切分，不要求录音迁就预估秒数。

## 5. 字幕

- 字幕按语义短句切分，每行建议不超过 18 个中文字符；
- 英文标识保留原大小写，例如 `Tool Call`、`Agent Loop`、`stopReason`；
- 代码标识用等宽体，但不要让整段代码占据手机屏幕；
- 口播说完整解释，屏幕只留下关键词和关系式；
- 字幕不能遮挡图中底部结论。

## 6. Mox 的使用

Mox 是讲解者和状态提示，不是装饰贴纸。常用状态包括：

- 普通讲解：肩部 X 模块常亮；
- 发现关键点：顶部橙灯闪烁；
- 调用工具：侧边模块展开或连出动作线；
- 风险提示：橙灯急闪，眼睛收窄；
- 完成总结：双手抬起或眨眼。

形象必须参考仓库内的标准设定图，身体比例、黑色面屏、橙色顶灯和肩部 X 模块保持一致。

## 7. 录音交付

推荐每章录成一个独立文件：

```text
01-from-llm-to-agent.wav
02-model-api-and-message-protocols.wav
...
18-observability-evaluation-and-harness-engineering.wav
```

建议 48 kHz WAV；如果手机录音只能导出 M4A，也可以直接使用。自然语速即可，不需要刻意卡秒。录音时读连续口播稿，不读分镜编号、英文括号说明或屏幕文字。

收到录音后的制作顺序是：降噪与响度统一 → 逐字转写 → 用真实停顿调整镜头 → 生成字幕 → 校对技术名词 → 渲染 → 手机实机检查。

## 8. 验收标准

- 不听声音也能通过画面看懂主线；
- 只听声音也能形成完整解释；
- 图、字幕和口播在同一时间解释同一件事；
- 首帧 2 秒内出现明确问题；
- 没有把模型请求画成已经执行的动作；
- 没有把某一家 Provider 的字段误写成通用协议；
- 没有超出安全区、文字重叠或低对比度；
- 结尾能独立形成一句可记住的判断标准。
